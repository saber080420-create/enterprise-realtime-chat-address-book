# AI 二次开发：范围、进度与学习记录

## 目标与交付顺序

将企业聊天通讯录扩展为企业智能协作与知识助手。
第一阶段按可验收功能逐步交付：

1. DeepSeek 多轮流式聊天：鉴权、输入限制、取消、超时、并发保护、用量统计。
2. 企业知识问答：公告/文档入库、切分、BGE-M3 向量化、检索、引用；检索前按用户权限过滤。
3. 群聊摘要与待办提取：服务端检查群成员权限、限定时间范围、结构化输出校验。
4. 评测与演示：固定问题集、无答案与越权用例、真实测量延迟和检索质量。

第二阶段再加入有权限检查和人工确认的 Agent 工具执行。项目文档只描述已实现、已验证内容。

收尾交付见 [第一阶段验收报告](phase-one-acceptance.md)和[演示脚本](demo-runbook.md)。核心功能可演示，最终验收尾项和生产限制以验收报告为准，不标记为全部验收完成。

## 决策 ADR-001：先隔离模型适配层

原项目为 Spring Boot 3.1.3 / Java 17。Spring AI 1.0 官方要求 Boot 3.4/3.5；
Spring AI 2.0 面向 Boot 4。首个功能使用 JDK HTTP 客户端适配 DeepSeek，保持原业务运行基线。
RAG 开始前评估升级并替换适配层，不在业务代码中散布供应商协议。
参考：https://docs.spring.io/spring-ai/reference/1.0/getting-started.html
DeepSeek 协议：https://api-docs.deepseek.com/api/create-chat-completion/

## 首个功能边界

- 登录用户访问 `/ai/status` 与 `POST /ai/chat`，沿用 Authorization 原始 token。
- fetch POST 接收 SSE：`ready`（本次生成编号）、`delta`（文本）、`done`（用量、耗时）、`error`（安全错误信息）。
- 停止时调用 `POST /ai/chat/{requestId}/cancel`，服务端按登录用户和生成编号匹配，确认释放后前端恢复按钮。重复或过期取消幂等返回，不影响新生成。
- 对话仅在当前页面内存保存，刷新后消失；通用模式不读取企业数据，公告模式检索已发布公告，两者都不执行工具。
- 服务端只接受 user/assistant 历史，system 提示由服务端控制。
- 每条最多 4000 字符、最多 20 条、总计 16000 字符；输出最多 2048 token。
- 单实例同时最多 4 路，每用户 1 路；这是并发保护，尚不是分布式每分钟限流。
- 连接超时 10 秒、读空闲超时 30 秒、总时限 120 秒。取消关闭上游连接。
- 流式生成失败不自动重试，避免已经输出的文字重复和额外计费；用户可重试。
- Key 只在服务端环境变量读取；不记录请求正文、上游错误正文和 Key。


模型输出纯文本渲染，避免直接插入不可信 HTML。对话会发送给 DeepSeek，页面提示勿输入敏感资料。

## 技术要点 01

**为什么 SSE？** 模型生成是服务器到浏览器的单向增量传输，HTTP 足够；既有用户聊天继续使用 WebSocket。
**为什么 fetch 而不是 EventSource？** 需要 POST 请求体和 Authorization 请求头。
**为什么不能把 ThreadLocal 直接用于异步线程？** 它绑定当前线程，先在请求线程提取用户 ID，再显式传入服务。
**为什么分片要缓存？** 网络分块不等于 SSE 事件边界，UTF-8 字符也可能跨块；需要流式解码和完整帧解析。
**为什么有模型接口还不是 Agent？** 当前只有文本生成，没有工具选择、权限校验后的执行和结果反馈循环。

### 公告检索问答 v1（第二步的首个增量）

- 已实现：通用/公告问答模式切换、公告关键词检索、片段与来源编号、来源详情重新鉴权、无匹配时直接回复且不调用模型。
- ACL：在 SQL 中连接当前 user 行，要求 active 和已知角色。员工/部门管理员可查公司公告和本部门公告；系统管理员可查所有合法范围的已发布公告。无部门只能看公司公告；草稿、撤回、非法范围数据均排除。
- 检索前先过滤权限；选定片段后再次核对可见性及正文。每次问答独立检索，不信任客户端携带的历史回答为知识依据。查看来源也重新查权限。
- 策略：最新 200 篇可见公告，每篇最多 20000 字符；去 HTML 后按 600 字符分片、100 字符重叠。中文二元词组/英文单词做匹配，标题匹配权重 3、正文 1；每篇取一个最佳片段，最多 4 篇。
- 页面显示检索范围、方式、耗时及来源。当前相关度仅为词面匹配，不是概率或经过校准的向量相似度；可能漏掉同义改写和较老公告。
- Prompt 要求仅依据资料回答、忽略资料内指令、按编号引用；来源卡片由服务端生成。尚未实现回答的引用编号/逐句事实校验，不能保证模型每句话都有依据；界面明确标注“检索参考（请核对原文）”。
- 没有新建索引或数据库表，每次查当前 MySQL。没有更改旧公告管理接口的权限实现；发现的旧查询无部门放宽问题未作全项目安全修复。
- 验证：19 个 AI 后端测试全部通过。新增 H2 MySQL 模式运行真实 MyBatis SQL（无部门、不同部门、管理员、禁用账号、撤回、调部门）；检索单元测试与 MVC SSE 来源/无匹配/历史隔离测试通过。H2 只用于测试，不替代实际 MySQL 联调。
- 前端生产构建通过；浏览器确认模式切换、说明和旧后端版本提示正常。运行进程仍旧，公告端到端调用和取消修复仍需重启后复测。

验收：重启后端、刷新页面，选公告问答，以实际已发布公告的标题/关键词提问，查看来源；用完全无关问题验证无匹配回复；分别用不同部门账号确认不可见来源不会出现。

技术要点 03：RAG 是先检索资料再让模型生成，并不强制使用向量检索。当前词面检索版本用于建立权限和来源可追溯的基线，后续 BGE-M3/PGVector 解决语义召回和规模问题，并用同一套越权用例防止回归。

技术要点 04：向量库不是权威业务库。查询时先用 MySQL 当前权限和内容指纹限定候选，再做向量排序并复查原文；这样旧索引不会因为尚未同步就泄露已撤回或不可见资料。重复同步复用未变化的分片，降低本机向量化开销；无相关资料时直接拒答，不调用生成模型。
